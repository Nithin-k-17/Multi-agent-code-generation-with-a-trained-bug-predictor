# Data Card (v3 Project Cycle)

## 1. Dataset Overview
- **Name:** MBPP LLM-Generated Bug Prediction Dataset (v3)
- **Primary Objective:** Train and evaluate CodeBERT on predicting whether a single, self-contained Python function generated by a code LLM contains a bug (fails test cases) or is clean (passes all test cases).
- **Generator Model:** `Qwen/Qwen2.5-Coder-1.5B-Instruct`
- **Source Problems:** Mostly Basic Python Problems (MBPP) - 974 problems with unit tests.

## 2. Split Methodology
To strictly adhere to zero-data-leakage principles:
- **Splits are partitioned strictly by Problem ID:**
  - **Prompt Split:** Task IDs 1 to 10 (official MBPP prompt tasks).
  - **Train Split:** Task IDs 11 to 510 (500 problems). Used exclusively for generating training candidates.
  - **Validation Split:** Task IDs 511 to 600 (90 problems). Used exclusively for threshold calibration and model selection.
  - **Held-Out Test Split:** Task IDs 601 to 974 (374 problems). Evaluated strictly ONCE at the end.
- **Contamination Guard:**
  - HumanEval is never touched for training, tuning, or threshold selection; reserved solely as an external out-of-distribution benchmark in Phase D.

## 3. Candidate Generation & Verification Pipeline
1. **Prompt Construction:** Each problem prompt includes the docstring / natural language task specification and function signature / test example.
2. **Sampling Configuration:** Temperature $T = 0.8$, top_p $= 0.95$, sampling 6 to 8 completions per problem.
3. **AST Filtering:** Completions that fail to parse with `ast.parse` are dropped.
4. **Sandboxed Test Execution:**
   - Each parsed candidate is executed against the problem's unit tests in an isolated Python subprocess with a 5.0s timeout.
   - **Labeling Rule:**
     - Passes all assertions with exit code 0: **Label 0 (Clean)**.
     - Fails assertions or raises runtime exception: **Label 1 (Buggy)**.
     - Timeouts (infinite loops) and non-terminating executions are dropped to prevent unverified hangs.
5. **Deduplication:** Exact text duplicate solutions within the same problem are eliminated.
6. **Balancing:** Both full (raw) and problem-balanced sets are maintained.

## 5. External Held-Out Benchmark: HumanEval
- **Source:** OpenAI HumanEval benchmark (164 hand-crafted functional programming problems).
- **Role:** Strictly held-out zero-shot generalization test (Phase D). Zero training, zero tuning, zero threshold calibration.
- **Generation:** Synthesized under identical conditions using `Qwen/Qwen2.5-Coder-1.5B-Instruct` ($T=0.8, \text{top\_p}=0.95$), 8 candidates per problem.
- **Verification:** Unit tests executed inside sandboxed subprocess with 5.0s timeout.

## 6. Combined Dataset Architecture (Phase C, Run 2)
- **Components:**
  1. `v3/data/train.jsonl` (MBPP LLM-generated code)
  2. `data_mutation/train.jsonl` (MBPP AST synthetic mutations, v2)
  3. `data/train.jsonl` (BugsInPy real-world repository diffs)
- **Objective:** Test whether combining real-world repository bugs and synthetic AST mutations with LLM-generated Python code improves model robustness and generalization or dilutes in-domain LLM pointwise accuracy.

## 7. Known Limitations
- Unit tests in MBPP verify functional correctness on specified test assertions; passing code may have unexercised edge-case bugs.
- LLM generation distribution is specific to Qwen2.5-Coder-1.5B-Instruct; transfer to other LLMs is tested on HumanEval in Phase D.
